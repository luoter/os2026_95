## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

- 本章节的核心主题是物理内存管理，建立在实验一已实现的可启动系统之上，主要解决操作系统如何认识、管理并映射物理内存的问题。实验二在实验一基础上使操作系统能够有序管理物理内存，并使程序通过虚拟地址访问内存
- 实验按照三个步骤推进，首先为发现物理内存，即获取系统中物理内存的数量与可用地址范围，然后为连续物理内存管理，即将物理内存按页划分，通过数据结构记录各页状态，实现页的分配与释放，从而保证内存使用的有序性，避免冲突与泄漏，其产出为可用的物理页分配器，最后为建立页表映射，即构建多级页表，将虚拟地址翻译为物理地址，设置页表项与权限，并使 CPU 使用该页表，因为程序访问的是虚拟地址，硬件必须依赖页表完成到物理地址的映射

### 2.2 功能的逐步实现

本实验在 Lab1 可启动内核的基础上，按照“识别物理内存—登记可用页—实现页分配—扩展对象分配—验证”的顺序推进。后一步都依赖前一步提供的内存信息或分配接口。

1. 首先探测物理内存。 内核从设备树取得物理内存的起始地址和大小，确定哪些地址属于可管理范围。只有先明确内存边界，后续建立页描述符和分配页面才不会访问无效区域。
2. 接着初始化物理页。 内核建立 Page 描述符数组，设置虚拟地址与物理地址的转换关系，并保留 OpenSBI、内核镜像及描述符数组占用的页面。选定物理内存管理器后，再通过 init\_memmap() 将剩余的完整空闲页交给它管理。这一步为各种分配算法提供相同且正确的初始内存状态。
3. 然后实现连续物理页分配。 先分析已有 First-Fit 如何查找、拆分和回收空闲块，再依照共同的 pmm\_manager 接口实现 Best-Fit，使分配器能够在满足请求的空闲块中选择较小者。在此基础上实现 Buddy System，按 2 的幂组织空闲块，支持大块拆分和伙伴合并。按这个顺序推进，便于复用已有接口，并比较不同算法对空闲块的管理方式。
4. 在页分配可用后实现 SLUB 扩展。 SLUB 先向底层页分配器申请页面，再在页面内分配小对象，并在整页对象全部释放后归还页面。它必须建立在可靠的物理页分配之上，因此安排在连续页分配功能完成之后。
5. 最后分层验证并联系分页机制。 分别检查物理内存初始化、Best-Fit、Buddy 和 SLUB 的分配与回收行为；同时核对页描述符、物理地址、内核虚拟地址以及启动页表地址之间的关系。宿主机测试用于检查算法边界，QEMU 用于观察内核中的实际运行结果，各项结果分别记录，避免用某一项测试代替整个系统的验证。

### 功能模块二：\[物理内存分配功能]

#### 任务一：\[理解first-fit连续物理内存分配算法]

**负责人：** \[2411191-王可]

1.first-fit分配器如何初始化空闲页：
default\_init\_memmap函数把从base开始的n个连续物理页登记为空闲内存：先逐页检查保留标志，再清除页面的标志和property，将引用计数设为0。随后设置base->property=n，标记base为空闲块首页，并按地址顺序将这个块插入空闲链表，同时执行nr\_free+=n。

2.first-fit分配器如何分配连续物理页：
对于default\_alloc\_pages，申请n页时，先检查空闲页总数是否足够，再从链表开头依次寻找第一个满足property>=n的空闲块，找到后立即停止，这就是first-fit。如果块大小恰好为n，就将整个块从链表中移除；如果块更大，就分配它前面的n页，把从page+n开始的剩余部分作为新的空闲块，放回原来的链表位置。最后减少nr\_free，清除已分配块首页的PG\_property标志，并返回首页的Page指针。

3.first-fit分配器如何回收页面并合并相邻空闲块：
default\_free\_pages函数先检查待释放页面的状态，清除页面标志并将引用计数归零，再把这n页登记成一个空闲块，按地址顺序插入链表，并增加nr\_free。插入后，先检查前一个空闲块是否满足：p+p->property==base；若满足，说明两块物理地址连续，可以合并，并将base更新为合并后块的首页。随后检查后一个空闲块是否满足：base+base->property==p，若满足，就继续向后合并。合并时累加页数、删除多余的链表节点，并清除被合并首页的PG\_property标志。合并只改变空闲块的组织方式，不改变空闲页总数。

4.原有的first fit算法是否有进一步的改进空间：
有，主要可以从查找效率、碎片管理和实现可靠性三个方面改进。可以提高查找效率：使用平衡树加速空闲块查找，或采用Next-Fit，减少从链表头重复扫描；可以改善碎片管理：在现有相邻空闲块合并的基础上，结合实际需求考虑其他分配策略，但需权衡查找开销和碎片问题；可以增强可靠性：增加重复释放、越界释放检查，并在多核环境下加入同步保护。

#### 具体实现方案

本扩展任务实现了一个单核教学版SLUB内存对象分配器，采用两层结构：

第一层复用ucore已有的物理页分配接口alloc\_pages()和free\_pages()，负责获取和归还物理页；第二层在物理页内部划分对象，向调用者提供slub\_alloc()和slub\_free()接口。

小对象采用16、32、64、128、256、512、1024、2048字节八个大小类。申请时选择能够容纳请求的大小类，使同一大小类的多个对象共享物理页。每个slab保存管理信息和空闲对象链，并通过位图记录对象是否已经分配。

分配器优先使用仍有空位的slab。slab被分配满后退出可分配链表；释放出对象后重新进入链表；全部对象释放后，将整页归还底层页分配器。另设活动slab登记表，记录包含满slab在内的全部活动区域，使释放操作能够先确认指针归属，再访问管理信息。

大于2048字节的对象使用连续物理页承载，并保存原始页申请参数，释放时按底层分配器的接口归还。该设计能够适配精确页数分配及Buddy的整块取整分配。

所有返回对象至少满足16字节对齐。申请0字节按1字节处理，容量不足或大小计算溢出时返回NULL，释放NULL为空操作。模块通过编译开关接入pmm\_init()，在物理页分配器可用后初始化。

本实现保留了SLUB按大小类管理对象、复用空闲对象、维护部分使用slab和回收空slab的主要思想，未实现多核并发、每CPU缓存和NUMA等机制。

#### 这些测试为什么能够有效检验实现

首先，大小类边界及相邻值测试能够检查对象是否被放入容量足够的大小类。例如，16字节和17字节请求应得到不同的容量保障。对请求范围逐字节写入和读取，可以发现对象空间不足、管理信息侵占有效数据区域等问题。

其次，多个对象同时存活时检查地址区间和数据内容，可以检验对象之间是否存在重叠。相比只检查返回指针非空，这种方法能够进一步发现错误复用仍被占用的对象、空闲链维护错误和数据互相覆盖。

批量分配、交错释放和重新填充能够反复触发slab从部分使用到满、从满到重新可用的状态变化。重新填充时要求不额外申请物理页，可以检验空位是否真正被复用。全部释放后检查页数恢复，则用于发现空slab或大对象的物理页泄漏。

底层内存耗尽测试进一步区分了“对象层仍有空位”和“物理页层已无空闲页”两种情况。前者仍应能够完成同大小类申请，后者需要返回NULL，同时保持已有对象不受影响，从而检验失败处理是否正确。

非法调用采用独立进程验证，只有明确走到SLUB代码中的预期断言出口才算通过，普通崩溃或sanitizer报错不能作为成功拒绝非法输入的证据。活动slab登记与对象位图共同用于检查指针归属和对象分配状态。

最后，4000次混合操作通过独立记录活动对象的信息检查长期状态变化，ASan和UBSan补充检查越界访问和未定义行为。这些测试能够覆盖主要功能和典型边界，但不代表穷尽所有可能的执行情况。

## gdb调试页表查询过程

### 1. 三终端搭建

按照先后顺序在三个终端内运行

终端1：`make debug`，QEMU 以 `-s -S` 启动后暂停在复位状态，等待 GDB 连接。

终端2（x86\_64 gdb）：调试宿主上的 QEMU C 源码。通过 `pgrep -f qemu-system-riscv64` 拿到 QEMU 进程 ID 后执行：

```
$ sudo gdb -p <PID>
(gdb) handle SIGPIPE nostop noprint
```

SIGPIPE 是 QEMU 正常运行时会收到的信号（GDB stub socket 断开时触发），不处理会导致 gdb 误中断。

终端3（riscv64-unknown-elf-gdb）：通过 QEMU GDB stub（localhost:1234）调试客户机内核：

```
$ make gdb
(gdb) b kern_init
(gdb) c
```

内核执行到 `kern_init` 入口处暂停，此时 satp 已开启，内核已在高地址空间运行。

### 2. 选择断点位置

为了观察 Sv39 页表遍历的真实执行过程，最初尝试在 `riscv_cpu_tlb_fill` 断住，但 QEMU 的 TLB 快路径会缓存命中后不再调用该函数；而 satp 开启前的几次命中 satp 值为 0，无法看到真实的页表翻译。

最终选择在 QEMU 的核心页表遍历函数 `get_physical_address` 设断点，并加上地址条件过滤：

```
(gdb) b get_physical_address
Breakpoint 1 at 0x... in get_physical_address at target/riscv/cpu_helper.c:158
(gdb) cond 1 addr>0xffffffff00000000
```

条件 `addr>0xffffffff00000000` 确保只在 satp 已开启、内核访问高地址虚拟空间时断住。低地址和 M 态恒等映射不会命中。

但内核在 `kern_init` 之后进入 `while(1)` 空转，没有新的高地址访存 → TLB 全命中 → CPU 不会触发 `riscv_cpu_tlb_fill` → `get_physical_address` 也不会被调用。

**解决办法**：利用 QEMU GDB stub 的调试读路径。GDB stub 需要读取客户机内存时，不查 TLB，而是直接调用 `riscv_cpu_get_phys_page_debug`，该函数内部无条件调用 `get_physical_address`（`target/riscv/cpu_helper.c:389`）。因此在终端3 执行任何需要读客户机内存的命令（如 `info registers`、`x/x addr`），终端2 就会命中断点。

### 3. 断点命中后的页表遍历观察

终端3 敲入 `info registers`，终端2 立即命中断点。以下是逐步调试的完整输出和分析：

#### 3.1 确认上下文

```
Thread 1 "qemu-system-ris" hit Breakpoint 1, get_physical_address (
    env=0x60fcd99c7060, physical=0x7ffc104c5658, prot=0x7ffc104c5650,
    addr=18446744072637931520, access_type=0, mmu_idx=1)
    at target/riscv/cpu_helper.c:158
```

- `addr = 18446744072637931520` = `0xffffffffc0206000`，高地址 VA，满足断点条件
- `mmu_idx = 1`，Supervisor 模式
- `access_type = 0`，这是 GDB stub 的调试读（非真实内存访问）

#### 3.2 检查 satp 寄存器

```
(gdb) p/x env->satp
$3 = 0x8000000000080205
```

satp 值正确。按 Sv39 格式拆分：

- MODE（bit 63-60）= `8` → Sv39 三级页表
- PPN（bit 43-0）= `0x80205` → 页表基址 = `0x80205 << 12 = 0x80205000`

这与 entry.S 中设置的 satp 完全一致。

#### 3.3 base 计算与页表索引

手动单步越过 L183-L184（`base = get_field(env->satp, SATP_PPN) << PGSHIFT`），然后检查 base：

```
(gdb) p/x base
# 预期应为 0x80205000
```

继续走到 L242，检查 L2 页表项的物理地址：

```
(gdb) n                    # 循环体入口，计算 idx
(gdb) n                    # L242: pte_addr = base + idx * ptesize
(gdb) p/x pte_addr
# 预期：VPN2 = (0xffffffffc0206000 >> 30) & 0x1FF = 0x1FF
#        pte_addr = 0x80205000 + 0x1FF * 8 = 0x80205FF8
```

#### 3.4 读取 PTE 并解析

继续走到 L254（ldq\_phys 已完成、ppn 已赋值）：

```
(gdb) p/x pte
$7 = 0x200000cf
```

这正是 entry.S 中 boot\_page\_table\_sv39 在 L2 根页表第 512 项（VPN2=0x1FF）写入的叶子 PTE。按 Sv39 PTE 格式拆分：

- flags（bit 9-0）= `0xcf` = V | R | W | X | A | D 全开
- PPN（bit 53-10）= `0x80000` → 物理页基址 = `0x80000 << 10 = 0x80000000`

内核虚拟地址 `0xffffffffc0206000` 处于这个 1GB 大页的覆盖范围内，翻译结果：

```
PA = (ppn << 10) + (addr & 0xfff) = 0x80000000 + 0x6000 = 0x80206000
```

偏移量 = `VA - PA = 0xffffffffc0206000 - 0x80206000 = 0xFFFFFFFF40000000`，这正是 memlayout.h 中定义的 PHYSICAL\_MEMORY\_OFFSET。

```
(gdb) p/x ppn
$8 = ...  # pte >> PTE_PPN_SHIFT，预期 0x80000
```

#### 3.5 验证翻译结果

执行 `finish` 跳出 `get_physical_address`，返回值 0 对应 `TRANSLATE_SUCCESS`。此时 `*physical` 指向的就是最终物理地址：

```
(gdb) finish
Value returned is $9 = 0        # TRANSLATE_SUCCESS
(gdb) p/x phys_addr             # 在调用者 riscv_cpu_get_phys_page_debug 中
# 预期应为 0x80206000
```

### 4. 完整的地址翻译

将上述断点观察到的值按 Sv39 规范串联起来：

```
satp         = 0x8000000000080205
  └─ MODE   = 8 (Sv39)
  └─ PPN    = 0x80205 → base = 0x80205000

addr (VA)    = 0xffffffffc0206000
  ├─ VPN2   = (addr >> 30) & 0x1FF = 0x1FF
  ├─ VPN1   = (addr >> 21) & 0x1FF = 0x000
  ├─ VPN0   = (addr >> 12) & 0x1FF = 0x006
  └─ offset = addr & 0xfff         = 0x000

pte_addr     = base + VPN2 * 8     = 0x80205FF8
pte          = 0x200000cf          (叶子 PTE)
  ├─ flags  = 0xcf (V|R|W|X|A|D)
  └─ PPN    = 0x80000

PA           = (PPN << 10) + offset = 0x80206000
```

整个地址翻译过程完全在 QEMU `get_physical_address` 的三级循环中完成，我们通过在该函数入口打断点、逐步检查局部变量，直接观察到了 satp 读取、页表基址计算、PTE 读取和物理地址拼接的每一步。

## 六、实验总结与收获

1. 对操作系统的理解：

   （1）物理内存的发现、保留与分配：

   OS 原理中，内存管理的重要职责是记录内存的使用情况，为不同使用者分配空间，并在使用结束后回收空间。
   本实验通过设备树获取物理内存的起始地址和大小，再排除 OpenSBI、内核镜像及页描述符数组等已经占用的区域，将剩余的完整物理页交给分配器管理。
   二者的联系在于，实验把“操作系统管理内存资源”这一抽象职责落实成了具体的初始化和分配流程。区别在于，原理分析经常从一片已经确定的空闲内存开始，而实际内核首先需要判断哪些内存存在、哪些已经被占用。硬件提供的物理内存不能全部直接作为空闲内存使用。

   （2）分页管理与物理页描述符

   OS 原理中的分页管理将虚拟地址空间划分为大小固定的页，将物理内存划分为对应大小的页框，通过页表建立二者之间的映射。
   本实验以物理页为基本管理单位，使用 struct Page 记录物理页的状态，并通过 alloc\_pages() 和 free\_pages() 完成分配与回收。
   需要区分的是：物理页是实际的存储空间，struct Page 是内核记录该空间状态的管理信息，页表项则用于描述虚拟地址与物理地址之间的映射。页描述符和页表项承担不同的职责，分配物理页也不等于已经建立了虚拟地址映射。

   （3）Buddy System 的拆分、合并与对齐

   OS 原理中的伙伴系统按照 2 的幂划分空闲块。没有合适的小块时，将较大的块逐级二等分；释放时，如果对应的伙伴也空闲，就逐级合并。
   本实验按照块的阶数维护空闲链表。申请时将页数向上取整为 2 的幂，例如申请 5 页时实际分配 8 页；释放时依据物理页号、块大小和状态判断是否能够合并。
   实验使我们进一步理解了伙伴关系的限制：两个块仅仅地址相邻、大小相同，并不足以证明它们是伙伴。 它们还必须属于同一个更大块的两个对半部分。因此，实现中需要正确处理物理地址对齐和伙伴边界，不能直接合并任意相邻空闲块。

   （4）虚拟地址、物理地址与地址转换

   OS 原理中，程序使用的虚拟地址需要通过 MMU 和页表转换为物理地址。地址转换在页内保持偏移不变，改变的是对应的页框位置。
   实验中，内核访问物理页及其管理信息时，需要区分虚拟地址、物理地址、物理页号和页描述符指针。已有的内核线性映射可以支持特定范围内的地址换算，但不能将这种固定偏移关系推广到任意虚拟地址。
2. 列出你们认为 OS 原理中很重要、但在本实验中没有对应上的知识点

   （1）请求分页与缺页异常处理
   请求分页允许程序只将当前需要的页面装入内存。当访问尚未装入的页面时，系统通过缺页异常完成页面分配、内容装入和映射更新。
   本实验主要完成物理内存的分配与回收，没有实现完整的按需装入和缺页处理流程。物理页分配器为这些机制提供基础，但不能独立完成虚拟存储管理。

   （2）页面置换、工作集与抖动
   FIFO、LRU、Clock 等页面置换算法用于在内存不足时选择需要换出的页面。工作集描述进程近期使用的页面集合，抖动则反映频繁换页导致系统有效工作减少的问题。
   本实验管理的是可供分配的物理页，没有根据进程的访问行为选择换出页面，也没有实现页面与磁盘之间的交换。Buddy 的空闲块合并属于空间管理，与页面置换的职责不同。

   （3）进程地址空间、共享与保护
   不同进程需要拥有受到保护的地址空间，同时又可能通过共享内存、共享代码页等机制共享资源。写时复制则可以推迟页面复制，减少不必要的开销。
   本实验虽然使用已有的内核地址映射，但没有完整实现多个用户进程的地址空间、进程间隔离、共享映射和写时复制。

### AI 协作开发的经验

1. AI 生成的代码需要通过测试和迭代验证。 我们通过检查申请页数取整、伙伴合并、重复释放和内存不足等情况，逐步完善实现。这个过程让我们认识到，代码能够编译并不代表功能正确，独立测试通过也不等于完整内核验证通过，需要结合测试结果判断完成程度。
